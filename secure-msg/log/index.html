11-02 21시

결정: 암호화를 빼고 통신부터

결정 김창식 · 분리 작업 Claude

암호화를 빼고 평문으로 통신부터 탄탄하게 하기로 했다. 사람끼리 메시지가 확실히 오가는 것을 먼저 보고, 그 위에 암호화를 한 단계씩 다시 얹는다.

암호화 코드는 지우지 않았다. 코드 페이지의 암호화 버전에 그대로 있다. 패킷 모양을 암호화 버전과 똑같이 남겨 둬서, 나중에 다시 얹을 때 서버 쪽은 거의 안 바꿔도 된다.

11-02 23시

서버를 따로 안 띄우는 방장 모드

질문 김창식 · 세 방법 비교와 구현 Claude

"서버와 클라이언트를 한 프로그램에서 할 수 있나?"를 따져 봤다. 길은 세 가지였다.

방법내용판단
1. 켤 때 역할 선택한 프로그램이 켤 때 서버나 참가자 중 하나가 된다쉽지만 서버 창은 여전히 따로
2. 방장이 중계+대화한 사람이 방을 열어 중계하면서 자기도 대화한다골랐다. 창 하나로 끝난다
3. 완전 P2P모두가 서로 직접 연결누가 누구에게 잇는지가 복잡해져 과제에 과하다

그래서 deolmi.c를 새로 만들었다. 이때는 아직 server.c · client.c · net.c · net.h 와 따로 있었다.

11-03

한 파일로 합침

요청 김창식 — "net.h 랑 net.c 합쳐줘", "실행이 한 파일에서 되게끔" · 구현 Claude

왜: 파일이 다섯 개로 나뉘어 있으니 받을 것도, 빌드 명령도, "어느 파일에 뭐가 있지?"도 많았다. 팀원이 받아서 바로 돌리려면 파일 하나, 명령 하나가 제일 쉽다.

어떻게:

  • net.c + net.h(패킷 주고받기)를 먼저 하나로 합치고, 이어서 전부 deolmi.c 안으로 옮겼다.
  • server.c의 중계 코드를 서버 모드와 방장 모드가 같이 쓰게 했다. 방장은 "자기도 방에 들어와 있는 서버"로 보면 된다. 그래서 방장 모드도 서버와 똑같은 규칙을 따른다 — 남의 이름으로 보내면 막고, 없는 사람에게 보내면 알려 준다. (예전 방장 모드에는 이 두 검사가 없었다.)
  • client.c의 대화 화면은 deolmi.c의 참가자 모드가 이어받았다. 참가자는 서버에도, 방장에게도 똑같이 붙는다.
  • 테스트 두 개는 deolmi.c의 통신 부분만 가져다 쓴다. 파일 맨 앞에 #define NET_ONLY 를 두면 ① 통신 부분까지만 읽히고 나머지는 건너뛴다.

설명서를 자세히, 암호화 계획 페이지를 새로

요청 김창식 — "지금까지 한 내용이 어떻게 작동되는지 자세하게 … 암호화를 어떻게 할 것이고 2인 잠금 시스템은 어떻게 진행할 것인지" · 작성 Claude

  • 설명서에 안에서 돌아가는 과정을 더했다 — 접속(소켓, 5초 제한, 실패 이유), 접속 절차(HELLO 그림), 실제 패킷 바이트, 한 통이 가는 길(거치는 함수 순서), 조각 모으기, poll 반복, 화면 그리기, 주소 표시. 팀 역할 표는 그대로 뒀다.
  • 암호화 계획을 새로 만들었다 — 무엇을 지키나, 쓰는 도구(libsodium), 키 두 종류, HELLO 서명, 단어 지문, 래칫, 받을 때 검사, 지금 코드에서 바뀌는 곳, 2인 잠금(키 두 개짜리 금고) 흐름과 바이트 모양, 막은 구멍, 못 막는 것, 만드는 순서 E1~V4. 11-02 암호화 버전 코드를 바탕으로 지금 한 파일·방장 방식에 맞게 다시 짰다. 공격 실험 명령은 계획에 넣지 않았다 (11-03 결정).
  • 코드는 바꾸지 않았다. 확인: 평문 테스트 25개, 11-02 암호화 버전 테스트 80개를 다시 돌려 모두 통과. 페이지의 서버 창 출력과 패킷 바이트는 실제로 돌려서 얻은 것이다.
11-04 오후

윈도우에서도 돈다 — WSL 없이

요청 김창식 — "저번에 줬던 test.c 파일처럼 윈도우에서도 되게끔" · 구현·시험 Claude

왜: 지금까지는 우분투(WSL) 창에서만 돌아서, 윈도우 노트북은 WSL 설치·미러링·Hyper-V 방화벽 규칙까지 해야 했다. 김창식이 준 test.c(winsock으로 만든 작은 채팅)처럼 윈도우에서 바로 빌드해 쓰게 했다.

어떻게: 파일을 나누지 않고 deolmi.c 맨 위에 #ifdef _WIN32 부분을 두어 윈도우와 다른 곳만 바꿨다. 리눅스 쪽 동작은 그대로다.

  • 소켓 — winsock(WSAStartup·closesocket·ioctlsocket·WSAPoll). 오류는 윈도우가 주는 한국어 설명으로 띄운다. 윈도우에서는 SO_REUSEADDR가 "같은 포트를 둘이 쓰기"라서 뺐다.
  • 키보드 — test.c는 입력용 스레드를 따로 두지만, 덜미는 치는 줄을 맨 아래에 다시 그리는 화면이라 스레드 없이 같은 구조를 지켰다. 소켓은 WSAPoll로 0.05초씩 기다리고 그 사이 키보드를 따로 본다. 키는 콘솔 함수로 하나씩 받아 UTF-8로 바꾼다.
  • 한글 — 화면을 UTF-8로 바꾸고, 명령줄의 이름도 UTF-8로 다시 받는다 (그대로 두면 윈도우에서 들어온 한글 이름이 리눅스 쪽에서 깨진다). 글자 폭은 윈도우에 wcwidth가 없어서 직접 잰다.
  • 주소 표시 — 윈도우는 가상 장치가 많아서, 인터넷 쪽으로 UDP connect만 해 보고 운영체제가 고른 주소 하나를 보여 준다. 방화벽 창에서 '액세스 허용'을 누르라는 안내도 뜬다.

확인: Visual Studio 2026으로 가장 엄격한 경고(/W4)에서도 경고 0 · 리눅스 테스트 그대로 통과 · 윈도우↔윈도우, 윈도우 방장↔리눅스 참가자, 리눅스 방장↔윈도우 참가자 대화(한글 이름, /dm) · Windows Terminal과 같은 방식(의사 콘솔)으로 실제 키를 쳐 넣어 한글·지우기·화살표·긴 줄·이모지·Ctrl+C 확인. 이모지가 사라지던 문제를 이 확인에서 찾아 고쳤다 (윈도우는 자판에 없는 글자를 "Alt 키를 뗐다"는 신호에 실어 보낸다).

확인 못 한 것: MinGW(gcc)로 하는 윈도우 빌드, 노트북 두 대 사이 실제 접속.

11-04 오후

방향: 방장이 서버 — 중계만 하는 서버 모드(--server)는 뺐다

결정 김창식 — "1대1이든 다수의 참여자가 있는 채팅이든간에 방장이 서버를 열고 나머지가 참여하는 방식을 사용할것", "없애" · 반영 Claude

정한 것: 덜미는 P2P(모두가 서로 직접 연결)가 아니다. 방장만 서버가 되고 나머지는 참가자로 들어온다. 1:1이든 여럿이든 같은 방식이다. 그래서 따로 띄우던 중계 전용 서버 모드를 뺐다.

암호화는 여전히 필요한가: 팀에서 "P2P면 중계자가 없어 운영자가 훔쳐볼 수 없으니 암호화가 필요 없다"는 의견이 나왔다. 김창식의 판단은 "암호화가 막으려는 대상은 중계자만이 아니라 둘 사이 네트워크 경로의 제3자이기도 해서 완전히 필요 없는 건 아니다"였다. Claude가 한 가지를 더했다: 덜미에서는 셋 이상이면 방장이 남들끼리의 글도 중계하므로, 방장 컴퓨터도 참가자끼리 암호화해야 하는 길목이다. 암호화 계획 01에 반영했다.

  • deolmi.c — 서버 모드, 서버 창의 [relay] 줄, 서버 안내 화면을 지우고 ③ 중계 칸을 방장 전용으로 정리했다.
  • 테스트 — make test가 서버 대신 방장 H를 켜고 돈다. 방장의 HELLO를 받는지, 방장 이름으로 못 들어오는지, 방장에게 보낸 글이 남에게 안 가는지 2개를 더해 27개.
  • 사이트 — 설명서(켜는 방식 두 가지, 한 통이 가는 길을 방장 기준으로 다시, 윈도우 설명), 시작하기(윈도우를 먼저), 암호화 계획(P2P 질문, 서버 창 예시 바꿈)을 고쳤다. 암호화 계획 페이지에서 crypto.c·vault.c 줄 수가 deolmi.c 줄 수로 잘못 나오던 것도 고쳤다 (273줄·304줄).

확인: 리눅스 make test 27개 통과, 윈도우 경고 0, 윈도우 방장↔참가자 대화와 실제 키 입력 다시 확인. 설명서의 "한 통이 가는 길" 화면은 방장 민지·참가자 수빈·현우를 실제로 띄워 얻은 출력이다.

11-05

통신만 남김 — 패킷에서 암호화 자리를 뺐다

요청 김창식 — "암호화 토대를 빼고 우선 통신이 되는 코드만 넣어줘. 암호화는 아직 안했다는 가정하에" · 구현·시험 Claude

왜: 평문 deolmi.c에 암호화를 나중에 얹으려고 미리 맞춰 둔 자리가 남아 있었다. 쓰지 않는 칸을 0으로 채워 보내는 코드라 "통신만 하는 프로그램"으로 읽기에 헷갈렸다.

  • 헤더 — seq(8바이트)·nonce(24바이트) 필드를 뺐다. 헤더는 종류·보낸 사람·받을 사람 33바이트(전에는 65). "안녕" 한 통이 76바이트에서 43바이트가 됐다.
  • HELLO — 키 자리였던 본문 128바이트(늘 0)를 뺐다. 이름만 보낸다. "HELLO 길이가 잘못됨" 검사도 없어졌다.
  • 패킷 종류 — 금고용 VAULT·OPEN_REQ·SHARE·PROOF를 뺐다. HELLO(1)·MSG(2)·SYS(3)만 남았다. 참가자가 MSG 말고 다른 걸 보내면 "모르는 type".
  • 전체 대화 — 전에는 사람마다 한 통씩 따로 보냈다(사람마다 키가 다를 것을 대비한 방식). 이제는 받을 사람을 비운 한 통을 보내고 방장이 모두에게 나눠 준다. 본문 맨 앞의 "모두에게/1:1" 바이트도 필요 없어져서 뺐다 — 받을 사람 필드로 안다.
  • 입장 — 새 사람에게만 기존 사람들의 HELLO를 준다. 기존 사람은 "○○ 입장" 알림으로 새 사람을 안다 (전에는 키를 나누려고 양쪽에 HELLO를 줬다).
  • 테스트 — seq·nonce 확인을 빼고, "HELLO 길이"·"VAULT도 그대로" 대신 "받을 사람이 빈 한 통이 모두에게 감", "보낸 사람에게는 안 돌아옴"을 넣었다. 그대로 27개.
  • 사이트 — 설명서 04~08·15와 첫 화면의 "바이트 직접 쳐 보기", 암호화 계획(지금 상태 설명, 바뀌는 곳 표, 만드는 순서 E1·E3·V1, 금고 종류 번호 4~7)을 새 모양에 맞췄다.

확인: 리눅스 make test 27개 통과(경고 0) · 방장 + 참가자 둘을 실제로 띄워 전체 대화·/dm·방장에게 1:1·/who가 각 화면에 맞게 뜨는지(1:1은 받는 사람에게만) · 윈도우 Visual Studio 빌드 경고 0, 윈도우 방장↔참가자 대화. 폴더의 deolmi.exe도 새로 빌드한 것으로 바꿨다 — 패킷 모양이 바뀌어 예전 버전과는 대화가 안 된다(둘 다 새로 빌드해야 한다).

방향 결정 김창식 — "교수님이 창의성을 중시하신다, 채팅 + 암호화는 시중에 너무 많다", "다른 플랫폼의 어떤 문제를 어떻게 보완하는지", "2026년 자료로", "그 방향으로 확정, 바로 진행" · 조사·설계·구현·시험 Claude

  • 장부 대조 — 사람별 전체 글 해시 사슬. 글 안에 번호와 앞 값을 넣고, 2초마다(새 글이 있으면)·/check로 맞춰 본다. 다르면, 빠지면 [덜미].

  • libsodium — 1.0.22 공식 Visual Studio 빌드를 받아 minisign 서명을 확인하고 libsodium\ 폴더에 넣음. 이 빌드가 C 런타임을 정적으로 써서 프로젝트도 /MT·/MTd. git이 .lib를 글자 파일로 보고 줄바꿈을 바꾸려 해서 .gitattributes에 binary로 지정.
  • 조사 중 고친 것 — 시험해 보니 ① 보낸 사람의 첫 글이 빠지면 "원래 0개"와 구분이 안 됨 → 멤버로 받아 줄 때 "여기서부터" 장부를 한 번 보냄 ② 나중에 들어온 사람은 기존 멤버 키를 안 적어 둬서 다시 접속할 때 자동 승인이 안 됨 → 처음 본 키로 적어 둠 ③ 이름 뒤 조사가 "창식가"처럼 어색함 → 받침에 맞게.

화면 지키기 — 찍으면 가려지고, 새면 잡힌다

요청 김창식 — "창의성이 좀 떨어지는 것 같다, 더 창의적이게", "카메라를 켜서 손날 가림막처럼 핸드폰을 인식하면 덜미가 잡히게", "같이 하자" · 설계·구현·시험 Claude

  • 왜 — 입장 심사는 시그널의 안전 번호 확인과, 장부 대조는 학계 연구와 닮아 "이미 있는 것"으로 보일 수 있었다. 그래서 누구나 겪는 문제인 캡처로 넓혔다. 2026년 9월 치협 선관위 단톡방(19명) 캡처가 소송 증거로 나왔는데 누가 흘렸는지 찾지 못했다 (계획 00).
  • 카메라 지킴이 (/eye, 김창식 아이디어) — python 도우미가 MediaPipe 물체 인식으로 화면을 향한 휴대폰이나 가려진 렌즈를 찾아 한 단어만 덜미에 보낸다. 덜미는 빈 화면 버퍼로 바꿔 끼워 글을 가리고, 방 사람들에게 EYE 패킷(암호화, 1바이트)으로 알린다. 영상은 저장·전송하지 않는다. 덜미가 꺼지면 도우미도 같이 꺼진다(job 객체).
  • 유출 추적 (/trace) — 카메라만으로는 키보드 캡처를 못 봐서 같이 넣었다. 두 사람 신원 키로 만든 표식 키로, 받은 글의 칸을 4칸에 1칸꼴로 두 칸 띄운다. 새어 나간 줄을 넣으면 사람마다의 표식을 다시 만들어 맞춰 본다. 내가 보낸 글만 되고, 덜미 첫 화면에 이 사실을 알린다.
  • 카메라 준비.bat (요청 김창식 "덜미 파일을 다운 받으면 저것도 함께 다운받게") — 실행 파일로 묶으면 80MB 안팎이라, zip은 그대로 두고 한 번 더블클릭하는 준비 파일을 넣었다. python이 없으면 winget으로 3.12를 내 계정에만 깔고 mediapipe==1.2.0(opencv가 같이 깔림)을 받는다. winget으로 깐 python은 PATH에 안 들어갈 수 있어서, 찾은 위치를 eye\python.txt에 적고 덜미가 그걸 먼저 쓴다. 카메라 프로그램이 바로 꺼지면 20초를 기다리지 않고 곧장 "카메라 준비.bat을 실행하세요"를 띄운다. 확인: python이 PATH에 있을 때와 없을 때(윈도우 스토어 바로 가기만 있을 때) 둘 다 준비가 끝나고 /eye가 켜짐, winget에 python 3.12가 있음. 아직: python이 아예 없는 노트북에서 winget으로 새로 까는 과정.
  • 시험하다 고친 것 — ① 다시 들어온 사람에게 카메라 상태가 안 갔나 했는데, 그 순간 "가려짐"이라 다른 문구로 간 것이었다 (테스트를 고침) ② 실제 창에서 가림막 화면을 읽어 보려니 다른 프로그램이 못 열게 돼 있었다 (공유 허용으로) ③ x64\Debug\deolmi.exe를 더블클릭하면 도우미를 못 찾았다 → exe 위쪽 폴더에서도 찾게 ④ "추적되는 방이라고 알린다"고 해 놓고 안내 줄이 빠져 있었다 → 첫 화면에 추가.

확인: 자동 테스트 105개 통과 · Debug·Release 빌드 경고 0 · 최소화한 실제 콘솔 창에서 휴대폰 신호 때 가림막으로 바뀌고 돌아오는 것을 화면 내용으로 확인 · 진짜 도우미를 노트북 카메라로 12초 돌려 휴대폰 없이 잘못 잡은 것 0 · 샘플 사진 5장 모두 휴대폰 찾음. 실제 휴대폰을 들어 보는 건 아직 (김창식 확인 필요).

  • 패킷 5개 (test_net) — 쪼개져 온 바이트, 붙어 온 두 통, 말도 안 되는 길이, 본문 0바이트, 번호·nonce가 그대로 전달됨
  • 중계 24개 (test_server) — 서명한 HELLO만 등록, 서명이 틀리면 거절 · 새 사람은 이미 있던 사람들의 HELLO(번호 1, 방장은 마지막 번호 2)를, 있던 사람들은 새 사람의 HELLO를 받음 · 같은 이름·빈 이름·방장 이름 거절 · 받을 사람에게만 · APPROVE·LEDGER도 그대로 넘김 · 받을 사람이 빈 글은 아무에게도 안 감 · 남의 이름 막기 · 20명째도 들어옴
  • 시나리오 46개 (e2e.py) — 방장 H와 참가자 A·B·C를 실제 deolmi.exe로 띄움: 승인 전엔 글이 안 감 → 전원 승인해야 멤버 → 전체·1:1 대화(1:1은 방장 화면에도 없음) → /check 모두 같음, 정상 대화에선 경고 0 → 두 얼굴을 B·C·H가 모두 잡고 보낸 A에게도 보임 → 방장이 버린 글을 장부와 번호로 잡음 → 1바이트 바꾼 글은 버리고 대화는 이어짐 → 같은 글이 H·B·C 화면에서 띄어쓰기가 서로 다르고, B·C 화면의 줄로 /trace 하면 각각 B·C를 찾음, 남의 글은 추적 안 함 → 가짜 카메라로 /eye: 휴대폰·가림을 방 사람 모두가 알고, 나중에 들어온 사람도 앎, 끄면 알림 → 같은 키로 다시 오면 자동 승인 → 같은 이름·다른 키면 경고하고 자동 승인 안 함

둘이서 채팅 — 직접 돌림

한 컴퓨터에서 프로그램 두 개를 띄우고, 정해 둔 순서대로 글을 넣어 양쪽 화면을 확인했다. 전체 대화, /dm 1:1, /who, 나가기까지 모두 맞게 떴다. 화면은 시작하기에 옮겨 두었다.

  • 방장 모드 — 민지(--host)와 현우
  • 셋이서 — 방장 민지 + 수빈 + 현우. 수빈이 모두에게 보낸 글이 방장 화면과 현우 화면에 뜨는 것까지 확인 (설명서 06)
  • 실제 창 — 콘솔 창 4개로 시연, Visual Studio로 켠 방장 + exe 더블클릭 참가자 (위 11-05)

위 자동 테스트와 시뮬레이션은 Claude가 돌렸고, 평문 버전을 실제 노트북에서 띄워 대화해 본 것은 김창식이다. 11-06 최종 버전은 아직 사람이 직접 창을 띄워 해 보지 않았다. 카메라 지킴이도 진짜 휴대폰을 들어 본 건 아직이다.

아직 확인 못 한 것 — 다른 컴퓨터에서 접속: 11-03 다른 데스크탑에서 시도했지만 연결이 이 노트북까지 오지 않았다. 학교 와이파이(SSU_INFO_WI-FI)가 기기끼리 연결을 막는 것으로 보고, 휴대폰 핫스팟으로 다시 해 볼 예정.
