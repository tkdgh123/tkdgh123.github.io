한 줄로

봉인 스티커를 메신저로 만들었습니다

노트북 상자에 붙은 "떼면 VOID 글자가 남는 스티커"를 떠올려 보세요. 스티커는 상자를 못 열게 막지 못합니다. 대신 누가 열었다면 반드시 흔적을 남깁니다.

덜미도 같은 생각에서 출발합니다. 메시지를 중계하는 서버는 마음만 먹으면 메시지를 바꾸거나, 대화 중간에 끼어들거나, 남의 이름으로 가짜 메시지를 보낼 수 있는 위치에 있습니다. 덜미는 서버를 믿지 않습니다. 서버가 그런 짓을 하면 사용자 화면에 경고가 뜨게 만듭니다. 그리고 정말 중요한 비밀은 두 사람이 함께 있어야만 열리는 금고에 넣습니다.

동아리 회계 인수인계

기본 · 종단간 암호화

서버 눈에는 이렇게 보입니다

A와 B는 처음 만날 때 공개키를 주고받아서, 둘만 아는 열쇠를 각자 계산해 냅니다. 열쇠 자체는 네트워크로 보내지 않습니다. 그 열쇠로 잠근 메시지만 서버를 지나갑니다.

열쇠는 두 사람마다 따로 있습니다. 그래서 대화 방식이 두 가지입니다. 그냥 입력하면 전체 대화가 되어, 접속한 사람마다 각자의 열쇠로 따로 잠가 보냅니다. /dm B를 치면 1:1 대화가 되어 B와의 열쇠로 잠근 메시지가 B 한 명에게만 갑니다. /all을 치면 다시 전체 대화로 돌아옵니다. 두 사람만 접속하면 그대로 1:1 메신저입니다.

읽은 대화는 원하면 내 노트북에만 남길 수 있습니다(선택 기능). 처음 실행할 때 비밀번호를 정하면, 메시지를 그 비밀번호에서 만든 열쇠로 잠가 파일에 쌓아 두고, 다음에 켤 때 비밀번호를 넣으면 /history로 다시 볼 수 있습니다. 서버에는 여전히 아무것도 남지 않고, 누가 파일을 몰래 고치면 열 때 들킵니다.

기본 · 메시지마다 바뀌는 열쇠

방금 한 말이 다음 열쇠가 됩니다

메시지를 하나 보낼 때마다 지금 열쇠에 방금 보낸 문장을 섞어 해시해서 다음 열쇠를 만들고, 쓴 열쇠는 지웁니다. 해시는 거꾸로 계산할 수 없으니, 나중에 누가 지금 열쇠를 훔쳐도 지난 메시지는 열지 못합니다. 이렇게 한쪽으로만 도는 톱니 같은 열쇠 사슬을 래칫(ratchet)이라고 부릅니다.

새 열쇠는 상대에게 보내지 않습니다. 그 문장은 보낸 A도 받은 B도 이미 알고 있으니, 둘이 각자 계산하면 똑같은 열쇠가 나옵니다. 열쇠가 네트워크를 지나가지 않으니 훔칠 것도 없습니다. 대신 서버가 메시지 하나를 몰래 빼면 B는 그 문장을 몰라서 다음 열쇠를 만들 수 없고, 그 자리에서 들킵니다.

실습 · 문장 섞기 래칫브라우저의 SHA-256으로 실제 열쇠를 만듭니다

정직하게 말하면, 지금 열쇠를 훔친 사람은 다음 메시지를 열어 그 문장을 알게 되므로 다음 열쇠도 계산할 수 있습니다. 문장을 섞어도 마찬가지입니다. 덜미가 지키는 건 지난 대화입니다. 문장을 섞지 않는 일반 래칫과 비교해도 보안상 차이는 거의 없습니다. 섞기는 팀의 처음 아이디어를 살린 것이고, 한 줄이 빠지면 그 뒤를 잠급니다.

팀의 처음 생각에서 고친 것

처음 아이디어는 "전 대화의 문장으로 새 열쇠를 만들어 상대에게 보내고, 받으면 지우기를 반복한다"였습니다. 쓰고 지우는 부분은 그대로 살렸고, 네 군데를 고쳤습니다.

문장만으로 만들지 않습니다

"ㅇㅇ", "ㅋㅋ", "밥 먹었어?" 같은 문장은 하나씩 넣어 보면 맞혀집니다. 그래서 비밀인 지금 열쇠에 섞습니다. 지금 열쇠를 모르면 문장을 맞혀도 소용없습니다.

열쇠를 보내지 않습니다

보내려면 그 열쇠를 또 무언가로 잠가야 하고, 이전 열쇠로 잠그면 이전 열쇠 하나가 그 뒤를 전부 엽니다. 양쪽이 각자 계산하면 보낼 필요가 없습니다.

방향마다 사슬이 따로 있습니다

여럿이 동시에 말하면 '직전 문장'이 사람마다 달라집니다. 그래서 A→B, B→A 사슬을 따로 두고, 내 사슬에는 내가 보낸 문장만 섞습니다.

빠지면 끊고 알립니다

빠진 건 순서번호가 건너뛰어서 알아채고, 문장을 모르니 그 뒤 열쇠도 못 만듭니다. 메시지가 저절로 빠지는 일은 없으니(TCP), 빠졌다면 서버가 뺀 것입니다. 다시 접속하면 새 열쇠로 이어집니다.

핵심 · 한글 단어 지문

서로의 단어 여덟 개를 소리 내어 맞춰 봅니다

서버가 처음부터 끼어들어서 A에게는 "내가 B야", B에게는 "내가 A야" 하고 자기 공개키를 내밀면 어떻게 될까요. 이걸 중간자 공격이라고 합니다. 막는 방법은 하나입니다. 상대의 공개키가 정말 그 사람 것인지 서버 바깥에서 확인하는 것입니다.

덜미는 각자의 공개키 지문을 한글 단어 8개로 보여 줍니다. 같은 방에서 "호랑이, 연필, 바다…" 하고 읽어 보면 됩니다. 단어 하나가 8비트라서 8개면 64비트입니다. 서버가 같은 단어가 나오는 가짜 열쇠를 찾으려면 수천만 년쯤 계산해야 합니다. 숫자 12자리를 쓰던 처음 설계는 몇 분이면 뚫렸습니다.

실습 · 단어 지문실습은 단어 64개로 간단히 했습니다. 실제 프로그램은 팀이 고른 256개를 씁니다

핵심 · 두 열쇠 금고

반쪽 열쇠로는 아무것도 알 수 없습니다

금고의 원리는 생각보다 단순합니다. 비밀과 같은 길이의 완전한 무작위 값 S1을 만들고, 비밀과 S1을 XOR(비트를 하나씩 비교해 같으면 0, 다르면 1)한 값을 S2로 둡니다. S1과 S2를 다시 XOR하면 비밀이 나옵니다. S1이 완전히 무작위라서 S2 하나만 봐도, S1 하나만 봐도 비밀에 대해 알 수 있는 게 전혀 없습니다.

정직하게

덜미가 못 하는 것

과장은 질문 하나에 무너집니다. 그래서 한계를 먼저 적어 둡니다.

  • 단어를 맞추기 전에는 모든 보호가 서버 앞에서 무력합니다. 처음 만났을 때 한 번은 꼭 소리 내어 확인해야 합니다.
  • 지금 열쇠가 새면 지난 메시지는 안전하지만, 그 뒤 메시지는 열립니다. 문장을 섞어도 마찬가지입니다. 훔친 사람이 다음 메시지를 열면 그 문장도 알게 되니까요.
  • 서버가 메시지를 일부러 빼면 대화가 끊깁니다. 들키지만 막지는 못하고, 다시 접속해야 이어집니다.
  • 금고에서 연 내용을 B가 베껴 적거나 화면을 찍는 건 막지 못합니다. 증명할 수 있는 것은 "C가 B에게 열쇠를 넘겼다"까지입니다.
  • 금고를 맡긴 A는 원래 내용을 압니다. 금고가 막는 건 받는 사람 한 명이나 서버가 혼자 여는 것입니다.
  • 누가 누구에게, 언제, 얼마나 보냈는지는 서버가 봅니다. 1:1 대화도 내용은 숨기지만 누구와 1:1로 대화하는지는 서버가 압니다.
  • 대화 기록을 켜면, 노트북과 비밀번호를 함께 뺏겼을 때 지난 대화가 열립니다. 래칫이 지켜 준 지난 메시지를 내가 일부러 남기는 것이라 기본은 꺼 둡니다.
  • 같은 Wi-Fi 안의 노트북끼리만 연결되고, 접속해 있지 않은 사람에게는 보낼 수 없습니다.

  1. 받았던 질문에 정면으로 답하기

    비교표 세 줄로 시작합니다. 카톡·Signal은 받은 사람이 혼자 열고, CyberArk·Vault는 서버 관리자가 원문을 보고, 덜미는 둘 다 안 됩니다.

  2. 동아리 회계 인수인계 시연

    A가 맡기고, B가 요청하고, C가 승인하고, 증명이 뜨는 정상 흐름을 보여 줍니다.

  4. 공격과 방어 한 쌍씩 설명 (각 2분)

    코드 슬라이드는 "라이브러리 한 줄"과 "직접 짠 줄"(패킷 구조, 길이 접두, 순서번호 검사, XOR 분할, 금고 흐름, 단어 지문)을 색으로 나눕니다.

#define HDR_LEN    (1 + NAME_LEN + NAME_LEN + 8 + NONCE_LEN)   /* 65 */

#define HELLO_LEN  (32 + 32 + 64)   /* 신원 공개키 + 세션 kx 공개키 + 서명 */

enum { T_HELLO = 1, T_MSG, T_VAULT, T_OPEN_REQ, T_SHARE, T_PROOF, T_SYS };

struct packet {
    uint8_t  type;

    uint64_t seq;
    uint8_t  nonce[NONCE_LEN];
    uint32_t body_len;
    uint8_t  body[MAX_BODY];
};

};

net.c 직렬화와 "덜 온 패킷" 처리
int send_packet(int fd, const struct packet *p)
{
    static uint8_t out[4 + HDR_LEN + MAX_BODY];
    uint32_t len = HDR_LEN + p->body_len;
    uint32_t nlen = htonl(len);
    uint8_t *q = out;

    memcpy(q, &nlen, 4);            q += 4;
    *q++ = p->type;
    memcpy(q, p->from, NAME_LEN);   q += NAME_LEN;
    memcpy(q, p->to, NAME_LEN);     q += NAME_LEN;
    for (int i = 7; i >= 0; i--)     /* seq: 큰 자리부터 */
        *q++ = (uint8_t)(p->seq >> (i * 8));
    memcpy(q, p->nonce, NONCE_LEN); q += NONCE_LEN;
    memcpy(q, p->body, p->body_len);

    size_t total = 4 + len, sent = 0;
    while (sent < total) {          /* send는 일부만 보낼 수 있다 */
        ssize_t n = send(fd, out + sent, total - sent, MSG_NOSIGNAL);
        if (n <= 0) return -1;
        sent += (size_t)n;
    }
    return 0;
}

int conn_take(struct conn *c, struct packet *p)
{
    uint32_t len;
    if (c->len < 4) return 0;
    memcpy(&len, c->buf, 4);
    len = ntohl(len);
    if (len < HDR_LEN || len > HDR_LEN + MAX_BODY) return -1;
    if (c->len < 4 + len) return 0;   /* 아직 덜 왔음: 다음 recv를 기다림 */

    const uint8_t *q = c->buf + 4;
    p->type = *q++;
    memcpy(p->from, q, NAME_LEN); q += NAME_LEN;
    memcpy(p->to, q, NAME_LEN);   q += NAME_LEN;
    p->from[NAME_LEN - 1] = p->to[NAME_LEN - 1] = '\0';
    p->seq = 0;
    for (int i = 0; i < 8; i++) p->seq = (p->seq << 8) | *q++;
    memcpy(p->nonce, q, NONCE_LEN); q += NONCE_LEN;
    p->body_len = len - HDR_LEN;
    memcpy(p->body, q, p->body_len);

    c->len -= 4 + len;              /* 꺼낸 만큼 앞으로 당긴다 */
    memmove(c->buf, c->buf + 4 + len, c->len);
    return 1;
}

struct packet은 64KB가 넘으니 함수 안 지역 변수로 두지 말고 static이나 전역으로 하나만 둡니다.
