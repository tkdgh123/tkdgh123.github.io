한 줄 요약
  • 메시지 — 두 사람마다 따로 맞춘 키로, 한 통마다 키를 바꿔 가며 암호화한다 (X25519 키 교환 + XChaCha20-Poly1305 + BLAKE2b 래칫). 중계하는 쪽은 암호문만 넘긴다.
  • 누구인지 — 사람마다 평생 쓰는 신원 키(Ed25519)로 서명하고, 그 키를 한글 단어 8개로 바꿔 만나서 맞춰 본다.

  • 약속은 "막는다"보다 "들킨다"다. 중계가 바꾸거나 다시 보내거나 빼먹으면 받는 화면에 경고가 뜬다.

01무엇을 지키나

덜미는 중계하는 방장과 네트워크 길목의 제3자(같은 와이파이, 공유기)를 믿지 않는 것에서 출발한다. 참가자의 글은 모두 방장을 거치고, 오가는 바이트는 길목에서도 보인다. 둘 다 마음만 먹으면 아래 일을 다 할 수 있는 자리에 있다.

중계·길목이 하려는 것지금 (평문)암호화 뒤
엿보기 — 글을 읽음그대로 보임암호문만 보임
바꾸기 — 글자 하나를 고쳐 넘김아무도 모름받는 쪽 경고 · 버림
다시 보내기 — 지난 글을 또 넘김아무도 모름받는 쪽 경고 · 버림
빼먹기 — 한 통을 안 넘김아무도 모름다음 통에서 들킴
남인 척 — 민지 이름으로 가짜 글지금은 이름 필드 검사뿐 (중계 자신은 막지 못함)서명이 안 맞아 버림

금고 열기—키 조각이 없어 못 엶

중계는 여전히 누가 누구에게 언제 얼마나 긴 글을 보내는지는 안다. 받을 사람 필드가 보여야 넘겨줄 수 있어서다 (아래 못 막는 것).

P2P면 암호화가 필요 없나?

팀에서 나온 질문이다. 둘이 직접 잇는 P2P라면 중간에 운영자가 없으니 "운영자가 엿보기"는 사라진다. 하지만 둘 사이 네트워크 길목의 제3자는 그대로라서, 그쪽을 막으려면 여전히 암호화가 필요하다. 게다가 덜미는 P2P가 아니다 — 방장이 서버가 되어 중계하므로, 셋 이상이면 방장도 남들끼리의 글이 지나가는 길목이다 (설명서 02).

02왜 종단간 암호화인가 — https 방식으로는 안 되는 이유

웹사이트의 https(TLS)는 나와 서버 사이만 암호화한다. 서버에 도착하면 복호화된다. 덜미에 그걸 쓰면 수빈→방장 구간, 방장→민지 구간은 암호화되지만, 가운데 방장은 다 읽는다. 셋 이상이면 방장이 남들끼리의 1:1까지 읽게 되니 소용없다.

그래서 보내는 사람이 암호화하고, 받는 사람만 복호화한다(종단간). 카카오톡 비밀채팅·Signal과 같은 생각이다. 중계 코드(③ 칸)는 내용을 몰라도 받을 사람 필드만 보고 넘기면 되니 거의 안 바뀐다.

03쓰는 도구 — libsodium

암호 알고리즘 자체를 직접 짜면 작은 실수 하나가 그대로 구멍이 된다. 그래서 알고리즘은 검증된 C 라이브러리 libsodium에 맡기고, 우리는 조립과 규칙(키를 언제 만들고, 무엇에 서명하고, 받을 때 무엇을 검사하는지)을 짠다.

하는 일알고리즘libsodium 함수왜 이것
키 교환 — 두 사람이 같은 키 만들기X25519crypto_kx_*공개키만 주고받고 각자 같은 키를 계산한다. 키 자체는 선을 타지 않는다
메시지 암호화XChaCha20-Poly1305crypto_aead_xchacha20poly1305_ietf_*암호화하면서 위조를 막는 인증 태그 16바이트를 붙인다. 1바이트만 바뀌어도 복호화되지 않는다. nonce가 24바이트라 무작위로 뽑아도 겹칠 걱정이 없다 — 헤더의 nonce 필드가 24바이트인 이유
다음 키 만들기BLAKE2bcrypto_generichash키를 넣어 쓰는 해시. 거꾸로 되돌릴 수 없다
신원·서명Ed25519crypto_sign_*신원 키로 한 서명은 공개키로 누구나 확인하지만 아무도 흉내 못 낸다
금고 조각 봉투X25519 + XSalsa20-Poly1305crypto_box_seal받는 사람 공개키로 봉하면 그 사람만 연다. 신원 키를 변환해서 쓰니 다음 접속에도 열린다
무작위 값운영체제 난수randombytes_buf키·nonce·금고 조각
지울 때—sodium_memzero컴파일러가 "안 쓰는 메모리니까" 하고 지우기를 빼먹지 않는다

06단어 지문 — 만나서 맞춰 보기

신원 공개키를 해시한 앞 8바이트를 단어 256개 표에 하나씩 대응시켜 한글 단어 8개로 바꾼다. 같은 키면 실행할 때마다 같은 단어다. 처음 만난 사람과는 옆에서(또는 전화로) 서로의 단어를 소리 내어 읽고 맞으면 확인 표시를 한다.

# 현우 화면 — 처음 만남 (단어는 예시)
[키] 민지 처음 만남 · 단어 고래-라면-등대-노을-탁구-혜성-냄비-참새 · 만나서 맞춰 보고 /verify 민지 ok
현우> /verify 민지 ok
[키] 민지 ✔ 확인한 키로 기억합니다
# 다음에 다시 접속했을 때 — 같은 키
[키] 민지 ✔ 전에 단어를 확인한 키
# 누가 중간에 끼어들어 키가 바뀌었을 때
[!] 민지의 키가 바뀜: 고래-라면-… → 사막-연필-…
    민지에게 단어를 소리 내어 다시 읽어 달라고 하세요 (/verify 민지)
  • 확인한 키는 ~/.deolmi/이름/known에 "이름 · 신원 공개키 · 확인했나"로 적어 둔다. 처음 한 번만 맞춰 보면 된다.
  • 왜 단어 8개인가 — 처음엔 숫자 12자리(40비트)였다. 40비트(약 1조 가지)는 끼어드는 쪽이 키를 계속 만들어 보며 같은 지문을 찾기에 짧다 — 그래픽카드면 몇 시간 거리다. 단어 8개는 64비트라 그보다 약 1,600만 배 어렵고, 숫자보다 읽어 주기 쉽다.
  • Signal의 "안전 번호"와 같은 장치다.

07메시지 암호화 — 한 통마다 바뀌는 키

두 사람이 HELLO를 주고받으면 kx_chains가 방향별 시작 키 CK₁을 만든다 (나→너, 너→나 따로). 보낼 때마다 이 키를 한 단계씩 앞으로 돌린다(래칫 — 한 방향으로만 돌아가는 톱니).

── 보낼 때 (n번째) ──
MK_n   = BLAKE2b(키 = CK_n, 내용 = "msg")              이 한 통만 암호화하는 키
암호문 = XChaCha20-Poly1305(MK_n, 평문_n, nonce, AD)  AD = 헤더의 종류·보낸 사람·받을 사람·seq
CK_n+1 = BLAKE2b(키 = CK_n, 내용 = "next" ‖ 평문_n)    방금 보낸 평문을 섞어 다음 키
CK_n, MK_n 지움                                        키는 보내지 않는다
── 받을 때 ──
같은 식으로 MK_n 계산 → 복호화해 봄 → 성공했을 때만 CK_n+1로 전진
헤더 필드지금암호화 뒤
seq01, 2, 3 … 두 사람 사이 방향마다 따로 센다
nonce0매번 새로 뽑은 무작위 24바이트
본문0/1 + 글(0/1 + 글)을 암호화한 암호문 + 태그 16바이트
종류·보낸 사람·받을 사람그대로그대로 보이지만 AD로 묶여서, 중계가 바꾸면 복호화되지 않는다
  • 지난 대화는 안전 — 옛 CK는 덮어써서 지운다. 지금 체인 키가 새어도 해시를 거꾸로 돌릴 수 없어서 지난 통은 못 연다. 다만 프로그램 메모리 전체가 털리면 그 접속(세션)은 위험하다 — 과장하지 않는다.
  • 다시 접속하면 새 세션 키로 CK₁부터 새로 시작한다.
  • 평문 섞기("next" ‖ 평문)는 우리 팀이 넣은 변형이다. 표준 래칫(Signal의 대칭 래칫)은 평문을 섞지 않는다. 솔직히 보안상 이득은 거의 없다. 대신 한 통이라도 빠지면 그다음 키를 만들 수 없어서, TCP라 빠질 일이 없다는 전제 위에 서 있다. 11-02 버전에 이미 들어가 테스트까지 통과했으니 그대로 쓴다.
  • 전체 대화는 지금처럼 사람마다 한 통씩 — 이제는 사람마다 다른 키로 암호화한 한 통씩이다. 16명이면 16번 암호화한다.
  • 방장 방식에서도 같다. 방장은 다른 사람끼리의 글을 중계만 하고 열지 못한다. 방장 앞으로 온 글만 방장이 연다.

08받을 때 검사 순서

받은 통마다 이 순서로 본다. 하나라도 걸리면 화면에 경고를 띄우고 그 통은 버린다. 경고 문구는 11-02 버전 코드 그대로다.

  1. 이 사람과 키가 있나? 없으면 [!] 키를 모르는 ○○가 보낸 메시지 · 폐기
  2. seq가 이미 받은 번호 이하인가? → 다시 보내기 [!] 순서번호 불일치: ○○의 #5 메시지는 이미 받은 번호 (재전송 의심) · 폐기
  3. seq가 건너뛰었나? (마지막+1이 아님) → 빼먹기 [!] ○○→나 #6 메시지를 못 받아서 그 뒤로는 열 수 없습니다: 대화가 끊겼습니다. 다시 접속하세요
  4. 복호화되나? 안 되면 → 바꾸기 [!] 변조 감지: ○○의 #6 메시지가 암호화한 그대로가 아님 (중간에 바뀜) · 폐기. 키는 앞으로 안 돌렸으니 진짜 6번이 오면 열린다 — 가짜 한 통으로 대화가 깨지지 않는다.
  5. 통과 → 키를 한 단계 돌리고, 받은 번호를 적고, 화면에 띄운다.

중계가 보내는 SYS 알림("○○ 입장" 같은 것)은 암호화하지 않는다. 그래서 암호화 뒤에는 목록을 서명이 맞는 HELLO로만 늘린다. 퇴장 알림은 그대로 믿는다 — 중계가 거짓 퇴장을 보내도 그 사람과 대화가 끊기는 것뿐이고, 몰래 읽히지는 않는다.

102인 잠금 — 키 두 개짜리 금고

민지가 비밀(예: 동아리 통장 비밀번호)을 금고에 넣고 현우와 수아 두 사람에게 맡긴다. 그 뒤로는 현우와 수아가 둘 다 동의해야만 열린다. 은행 금고의 열쇠 두 개, 핵 발사 열쇠 두 개와 같은 생각이다.

누가혼자 열 수 있나이유
현우못 엶자기 조각 S1만 있다
수아못 엶자기 조각 S2만 있다
중계 (방장)못 엶조각이 현우·수아 신원 키로 봉해져 있다
민지 노트북못 엶맡기고 나면 키와 조각을 지운다 (민지는 원래 내용을 안다)
현우 + 수아엶이게 목적. 수아가 승인하면 현우 화면에 뜬다

원리 — XOR로 반 나누기

XOR은 비트를 하나씩 비교해 같으면 0, 다르면 1. 비밀과 같은 길이의 완전한 무작위 값 S1을 뽑고, S2 = 비밀 ⊕ S1로 둔다. S1 ⊕ S2를 하면 비밀이 다시 나온다. S1은 그냥 무작위고 S2도 무작위처럼 보여서, 한 쪽만 봐서는 비밀에 대해 아무것도 알 수 없다. 직접 해 보기:

비밀 (바이트)
S1 — 현우 조각 (무작위)
S2 — 수아 조각 (비밀 ⊕ S1)
S1 ⊕ S2

실제로는 비밀을 직접 나누지 않는다. 무작위 암호화 키 L(32바이트)로 비밀을 암호화하고, 그 L을 위처럼 S1·S2로 나눈다. 비밀 길이와 상관없이 조각은 늘 32바이트다.

11금고 흐름

모든 화살표는 중계를 거친다. 중계는 받을 사람 필드만 보고 넘긴다. 중계가 아무것도 보관하지 않으니 맡길 때와 열 때 관련된 사람이 접속해 있어야 한다.

#누가 · 무엇을중계가 보는 것
1민지 — 암호화 키 L로 내용 암호화 → L = S1 ⊕ S2 → (S1 + 제목)을 현우 신원 키로, (S2 + 제목)을 수아 신원 키로 봉투에 넣기 → 묶음 전체에 서명 → 둘에게 한 통씩 보내고 L·S1·S2 지움암호문, 봉투 2개, 서명
2현우·수아 — 민지 서명 확인 → 자기 봉투만 열어 제목 확인 → 묶음을 ~/.deolmi/이름/vault/에 저장—
3현우 /open 제목 — 금고 번호에 서명한 열람 요청을 수아에게금고 번호, 서명
4수아 — 현우 서명 확인 → 화면에 무엇을 누가 열려는지 뜸 → /approve → 자기 조각 S2를 현우만 열게 다시 봉하고, 키 전달 증명에 서명 → 자기 사본 지움, 승인한 번호 기억현우만 여는 봉투, 서명
5현우 — 수아 서명 확인 → S1 ⊕ S2 = L → 내용 열기 → 30초 뒤(또는 엔터) 화면·스크롤 지움 → 묶음 지움 → 증명을 모두에게 (래칫으로 암호화해서)암호화된 증명
  • 금고 번호는 중계가 붙이지 않는다. 서명까지 된 묶음의 해시(BLAKE2b 32바이트)를 번호로 쓴다. 중계가 번호를 바꿔치기할 수 없다.
  • 봉투가 신원 키로 봉해져 있어서 다음 접속에도 열린다. 세션 키로 봉했다면 끄는 순간 못 열게 된다.
  • 한 번 열면 끝이다. 현우는 묶음을, 수아는 사본을 지운다.

12금고 묶음의 모양

보유자 116보유자 216현우 봉투112수아 봉투112내용 암호문내용 + 16민지 서명64
  • 봉투 112바이트 = 키 조각 32 + 제목 32 + 봉투가 붙이는 48. 제목을 32바이트로 고정해서 길이로 제목을 짐작하지 못한다. 제목은 봉투 안에만 있어서 중계는 모른다.
  • 내용은 1000바이트까지. 패킷 종류는 VAULT(3), 지금 헤더의 nonce 필드에 내용을 암호화한 nonce가 들어간다.
  • 저장 — ~/.deolmi/이름/vault/번호앞8바이트.vault (0600). 불러올 때마다 서명을 다시 확인한다. 파일을 누가 고쳤으면 [!] 금고 파일이 바뀌어 서명이 안 맞음.
  • 키 전달 증명 = 금고 번호 · 제목 · 시각 · 맡긴 사람 · 요청한 사람 · 승인한 사람 + 현우 서명 + 수아 서명. "누가 누구에게 언제 키를 넘겼다"를 둘 다 부인할 수 없다.
종류번호보내는 쪽 → 받는 쪽본문
VAULT3민지 → 현우, 민지 → 수아위 묶음

이 네 종류 번호는 지금 코드에도 자리가 잡혀 있고, 중계는 이미 내용을 안 보고 넘긴다. test_server.c의 "MSG가 아닌 type(VAULT)도 to에게 그대로"가 확인한다.

14미리 막은 구멍

11-02 설계를 검토하면서 찾은 구멍과 막는 법이다. 코드를 옮길 때 이 줄을 빼먹으면 구멍이 다시 열린다.

심각도구멍막는 법
치명봉투는 보낸 사람이 익명이라, 중계가 "민지의 금고"를 위조할 수 있다민지가 신원 키로 묶음 전체(보유자 둘, 봉투 둘, 암호문, nonce)에 서명. 금고 번호도 묶음 해시
치명지문이 세션 키만 덮으면, 중계가 봉투용 공개키를 바꿔치기해 두 조각을 다 연다지문은 신원 키 하나만. 봉투 키는 신원 키에서 변환. 세션 키에는 신원 키 서명
높음숫자 12자리(40비트) 지문은 같은 지문이 나오는 키를 몇 시간이면 찾는다단어 8개(64비트)
중간제목 해시를 평문으로 보내면 중계가 "통장 비번" 같은 흔한 제목을 넣어 맞혀 본다제목은 봉투 안에만. 제목이 든 증명도 래칫으로 암호화해 보냄
중간승인하는 사람이 무엇을 승인하는지 모르고, 요청·승인에 서명이 없다제목을 보유자 둘에게 봉해 보냄(길이 고정). 요청과 승인에 서명
참고풀기에 실패해도 래칫이 돌면 가짜 한 통으로 대화가 깨진다성공했을 때만 전진
참고중계가 예전 열람 요청을 다시 보낸다승인한 금고 번호를 기억해 두 번째는 거절
참고세션 키까지 신원 키에서 만들면 접속마다 같은 키가 나온다세션 키는 매번 새로, 신원 키로는 서명만

15못 막는 것

  • 누가 누구에게 언제, 얼마나 긴 글을 보내는지는 중계가 안다. 넘겨주려면 받을 사람 필드를 봐야 해서다.
  • 빼먹기·끊기 자체는 막지 못한다. 들킬 뿐이다. 중계가 다 버리면 대화가 안 된다.
  • 처음 만났을 때 단어를 안 맞춰 보면 중계가 그때부터 끼어들 수 있다. 그래서 확인 전에는 경고를 띄운다.
  • 내 노트북이 해킹되면 신원 키 파일과 화면이 다 털린다.
  • 금고에서 연 내용을 베껴 적거나 화면을 찍는 것. 증명할 수 있는 건 "수아가 현우에게 키를 넘겼다"까지다.
  • 현우와 수아가 짜고 열면 열린다 — 그게 2인 잠금의 정의다. 맡긴 민지는 원래 내용을 안다.
  • 중계가 아무것도 보관하지 않으니, 맡길 때와 열 때 관련된 사람이 동시에 접속해 있어야 한다.
