0프로젝트 이해

서버를 만들기 전에 프로젝트 전체를 어떻게 이해하고 있는지 정리했습니다. 근거는 팀 단톡방(9. 23.~10. 21.), 제안서(10. 7.), 팀 기획서 수정본(10. 21.)입니다. 잘못 이해한 곳이 있으면 이 절부터 고쳐 주세요.

한 줄 요약

서버도 내용을 볼 수 없는 C 언어 종단간 암호화 채팅. 메시지마다 키가 바뀌어서 지금 키가 털려도 지난 대화는 안전하고, 중요한 메시지는 두 사람이 모여야만 열립니다.

할 수 있는 것: 기능 7가지

A, B, C 세 사람이 접속해 있다고 하고, 각 기능을 쓰면 화면에 무엇이 보이는지 적었습니다.

기능이렇게 쓴다화면에 보이는 것설명
1. 접속./client --user B --server 192.168.0.12:9000[*] 서버 연결 완료
[*] 접속 중: A, C		이름을 정하고 대화방에 들어갑니다. 이미 있는 이름이면 거절됩니다.
2. 일반 메시지그냥 글자를 치고 EnterB, C 화면: [A] 내일 회의 3시야접속해 있는 모든 사람에게 갑니다. 서버에는 알아볼 수 없는 바이트만 지나갑니다.
3. 안전번호 확인/verify AA와의 안전번호: 4821 0937 1150A도 /verify B를 쳐서 두 사람이 숫자를 소리 내어 맞춰 봅니다. 같으면 서버가 중간에서 키를 바꿔치기하지 않은 것입니다.
4. 잠금 메시지 보내기A: /lock B C 금고 비번은 4512A: [*] 잠금 #3 보냄
B, C: [잠금] A의 잠금 메시지 #3 (B, C 둘 다 동의해야 열림)		B와 C에게 번호만 도착하고 내용은 보이지 않습니다. 열쇠를 반으로 쪼개 B와 C가 반쪽씩 가진 상태입니다.
5. 열람 요청B: /open 3B: [!] C의 승인을 기다리는 중
C: [요청] B가 #3을 열려고 합니다 → /approve 3		B 혼자서는 열 수 없습니다. 반쪽 열쇠로는 아무것도 알 수 없습니다.
6. 승인C: /approve 3B: [#3] 금고 비번은 4512C가 자기 반쪽을 B에게만 넘겨 B가 엽니다. 읽는 사람은 요청한 B 한 명, 한 번뿐이고, 열리면 #3은 서버에서도 지워집니다. 승인한 C는 내용을 보지 못합니다.
7. 종료/quit다른 사람 화면: [*] B 퇴장내 컴퓨터의 키를 전부 지우고 끝냅니다. 내가 반쪽을 가진 잠금 메시지도 함께 사라집니다.

하지 않는 것

  • 대화 기록 저장 없음. 프로그램을 끄면 대화가 사라집니다. 파일에 남기지 않는 것도 보안 설계의 일부입니다.
  • 접속해 있지 않은 사람에게는 보낼 수 없음. 나중에 접속해도 지난 메시지를 받지 못합니다.
  • 1:1 귓속말 없음. 일반 메시지는 접속자 전원에게 갑니다. 특정 두 사람을 지정하는 건 잠금 메시지뿐입니다.
  • 글자만 보냄. 파일과 사진은 보내지 않습니다.

어디서 실행하나: 설치형

설치형으로 결정했습니다 (10. 29.). 각자 컴퓨터에 프로그램을 설치해서 실행하는 방식이고, 웹 버전은 만들지 않습니다. 프로그램은 두 개입니다.

  • server: 중계 서버. 딱 한 대에서만 켭니다.
  • client: 채팅 프로그램. 대화하는 사람마다 하나씩 켭니다.

서버도 그냥 프로그램 하나라서 데스크탑이든 노트북이든 아무 컴퓨터에서나 켤 수 있습니다. 서버 전용 컴퓨터도 필요 없어서, 서버를 켠 노트북에서 client를 같이 켜고 대화에 참여해도 됩니다. 따라서 노트북끼리만으로도 충분히 됩니다.

상황구성client에 넣는 서버 주소설정
① 혼자 개발·테스트컴퓨터 1대에서 터미널 4개 (server 1개 + client 3개)127.0.0.1:9000 (자기 자신)없음
② 발표 시연노트북 1대가 server + client A, 다른 노트북 2대가 client B, C. 모두 같은 Wi-Fi서버 노트북의 IP (예: 192.168.0.12:9000). 서버 노트북 자신은 127.0.0.1:9000서버 노트북만 한 번 (아래)
③ 서로 다른 장소 (집 ↔ 학교)인터넷 너머로 연결공인 IP공유기 포트포워딩이나 클라우드 서버가 필요 → 이번 범위 밖
        같은 Wi-Fi (발표 때는 휴대폰 핫스팟 추천)

  노트북 1  IP 192.168.0.12
    ./server
    ./client --user A --server 127.0.0.1:9000

  노트북 3  ./client --user C --server 192.168.0.12:9000   ──▶ 노트북 1
서버 컴퓨터에서만 할 설정 (②):
  • 서버는 모든 주소에서 연결을 받도록 0.0.0.0(INADDR_ANY)에 bind합니다. net_listen이 이렇게 만들어야 합니다.
  • WSL2는 기본 설정으로는 다른 컴퓨터에서 들어오는 연결을 WSL 안까지 넘겨주지 않습니다. Windows 11에서는 %UserProfile%\.wslconfig에 networkingMode=mirrored를 넣는 방법과 netsh interface portproxy로 9000번을 넘겨주는 방법이 있습니다. 거기에 Windows 방화벽에서 TCP 9000 허용이 필요합니다. 정확한 절차는 WSL 설치 후 직접 해 보고 이 문서에 고정합니다.
  • 학교 Wi-Fi는 같은 Wi-Fi에 붙은 기기끼리의 접속을 막아 두기도 합니다. 시연 때는 휴대폰 핫스팟 하나에 노트북을 모두 연결하는 편이 안전합니다.
  • client 쪽 컴퓨터는 설정할 것이 없습니다. 밖으로 나가는 연결이라 막히지 않습니다.

설치 방법: 개발 환경과 똑같이 WSL2(Ubuntu)에 libsodium-dev를 깔고 make로 빌드합니다. Windows에서 더블클릭하는 .exe로 만들려면 소켓 코드(Winsock)와 키보드 입력 처리를 다시 짜야 해서 이번 범위에서는 하지 않고, 확장 과제로 둡니다.

왜 만드나: 세 가지 문제와 답

문제우리 답한계 (정직하게 적어 둘 것)
① 키 하나가 뚫리면 지난 대화 전체가 노출메시지 키 래칫: 메시지마다 새 키를 만들고, 쓴 키는 지움. 한 방향 계산이라 지금 키로 옛 키를 되돌릴 수 없음지금 키를 훔치면 다음 키는 계산 가능. 미래 보호(DH 래칫)는 확장 과제
② 서버나 기기 하나만 털려도 혼자 열람 가능서버는 암호문만 중계(종단간). 중요한 메시지는 2인 합의 잠금: 키를 XOR로 두 조각 내 각자의 공개키로 봉인보낸 사람은 원래 내용을 앎. 막는 건 "받는 쪽 한 명 또는 서버가 혼자 여는 것"
③ 암호화만으로 공격을 막는지 알 수 없음변조 → 인증 암호(AEAD), 재전송 → 순서번호, 중간자 → 안전번호 비교. "나쁜 서버" 옵션으로 직접 공격해서 막히는 걸 보여줌시연은 우리가 정한 3가지 공격에 한함

속에서 일어나는 일 (개발자용)

  안전번호 4821 0937 …  ◀──────────── 두 사람이 말로 비교 ────────────▶  같으면 중간자 없음
  CK → MK 래칫 → 암호화 ── MSG(암호문) ──▶ to 보고 전달만 ──▶ 래칫 → 복호화 → 쓴 키 삭제

발표에서는 원리를 AES와 공개키로 설명했지만, 실제 구현은 어느 PC에서나 같은 결과를 내도록 XChaCha20을 씁니다(제안서 → 수정본에서 바뀐 부분).

질의응답에서 나온 질문에 대한 지금의 답

  • 패킷이 유실되거나 순서가 바뀌면? TCP라서 순서는 보장됩니다. 순서번호가 건너뛰면 그만큼 래칫을 앞으로 돌리고(최대 50개), 작으면 재전송으로 보고 버립니다. 지우는 것은 지난 키이지 메시지가 아닙니다.
  • 배포는 웹인가 설치형인가? 설치형입니다(10. 29. 결정). 각자 컴퓨터에 client를 설치하고, 한 대가 server를 켭니다. 위 "어디서 실행하나"를 참고하세요.
  • 시중에 이미 있지 않나? 종단간 암호화와 키 래칫 자체는 Signal 같은 메신저에 있습니다. 차별점은 "두 사람이 모여야 열리는" 2인 합의 잠금이고, 직접 구현해 공격을 막는 것까지 보여주는 데 의미를 둡니다.

1서버가 하는 일과 하지 않는 일

서버는 우체국입니다. 봉투(헤더)에 적힌 받는 사람에게 전달할 뿐, 봉투 안(암호문)은 열 수 없습니다. 서버가 키를 한 번도 갖지 않아야 문제 ②(서버 단독 열람)에 대한 답이 됩니다.

한다하지 않는다
여러 클라이언트 접속을 동시에 받는다 (poll)메시지를 복호화하지 않는다 (개인키·메시지 키가 없음)
이름과 공개키 2개를 등록받고, 다른 사용자에게 나눠 준다순서번호(seq)를 검사하지 않는다 (클라이언트 몫)
헤더의 to를 보고 해당 사용자에게 패킷을 전달한다대화 내용을 파일·DB에 저장하지 않는다
잠금 메시지(암호문 + 봉인된 조각 2개)를 보관하고, 열람 요청을 중계한다봉인된 조각을 열지 않는다 (받는 사람 공개키로 봉인됨)
입장·퇴장·오류를 SYS로 알린다libsodium으로 암호화하지 않는다 (--mitm 시연용 키 생성만 예외)
시연용 "나쁜 서버" 옵션: --tamper --replay --mitm

2구조

스레드 없이 poll() 하나로 돌아가는 단일 루프로 만듭니다. 리스닝 소켓과 접속한 클라이언트 소켓을 모두 poll에 걸어 두고, 읽을 거리가 생긴 소켓만 처리합니다. 스레드를 쓰지 않으니 락(mutex)도 필요 없습니다.

main()
 ├─ net_listen(9000)                  소켓 생성 · SO_REUSEADDR · bind(0.0.0.0) · listen
 └─ for (;;) poll(fds, n, -1)
      ├─ 리스닝 소켓이 읽기 가능 → accept → 클라이언트 표에 추가
      └─ 클라이언트 소켓이 읽기 가능 → recv → 그 클라이언트의 버퍼 뒤에 붙임
            └─ 버퍼에 패킷이 "통째로" 모였으면 하나씩 꺼내 handle_packet()
                  ├─ HELLO    → 등록 + 공개키 배포
                  ├─ MSG      → to에게 그대로 전달
                  ├─ LOCK     → 잠금 표에 보관, 번호 붙여 알림
                  ├─ OPEN_REQ → 요청자에게 자기 조각, 다른 보유자에게 승인 요청
                  └─ SHARE    → 요청자에게 전달 후 잠금 삭제

서버가 들고 있는 상태

표칸크기
클라이언트 표소켓 fd, 이름(16), 키 교환 공개키(32), 봉인용 공개키(32), 등록 여부, 받는 중인 버퍼와 길이최대 16명
잠금 표번호, 보낸 사람, 보유자 2명, 봉인된 조각 2개(각 80바이트), nonce(24), 암호문, 열람 요청한 사람최대 64개

둘 다 고정 크기 배열이면 충분합니다. 연결 리스트나 해시 테이블은 필요 없습니다. 이름으로 찾을 때도 16칸을 처음부터 훑으면 됩니다.

3패킷 형식

팀 기획서 6절과 같습니다. TCP는 경계 없이 바이트가 이어서 흘러오기 때문에, 맨 앞 4바이트에 뒤따르는 길이를 적어 패킷을 구분합니다.

length4B
type1B
from16B
to16B
seq8B
nonce24B
body가변 (최대 64KB)
  • length = 헤더 65바이트(1+16+16+8+24) + body 길이. 네트워크 바이트 순서(htonl).
  • seq는 8바이트라 htonl이 없으니 시프트로 한 바이트씩 직접 씁니다(큰 자리부터).
  • 이름은 최대 15글자, 남는 칸은 0으로 채웁니다.
  • 구조체를 그대로 send하지 않습니다. 컴파일러가 칸 사이에 패딩을 넣을 수 있어서 바이트 배열에 한 칸씩 복사(직렬화)합니다.

type별 body

봉인 조각이 80바이트인 이유: 조각 32바이트 + crypto_box_SEALBYTES(48바이트).

52인 합의 잠금 중계 순서

팀 기획서 5-3절의 흐름을 서버 쪽에서 본 것입니다. A가 잠금 메시지를 보내고 B와 C가 조각을 하나씩 갖는 경우입니다.

#흐름패킷서버가 하는 일
1A → 서버LOCKB, C가 접속 중인지 확인 → 잠금 표에 저장, 번호 3 부여
2서버 → A, B, CSYSA에게 "잠금 #3 등록", B와 C에게 "A의 잠금 메시지 #3 (B, C)"
3B → 서버OPEN_REQ seq=3B가 #3의 보유자인지 확인, 요청자 = B로 기록
4서버 → BLOCK seq=3B의 봉인 조각 + 암호문 전달 (B는 아직 반쪽뿐이라 못 엶)
5서버 → COPEN_REQ seq=3C의 봉인 조각 전달. C 화면에 "B가 #3 열람 요청, /approve 3"
6C → 서버SHARE to=B seq=3C가 #3의 다른 보유자이고 요청자가 B인지 확인
7서버 → BSHARE seq=3전달 후 잠금 #3을 표에서 지움 (한 번만 열람)

제안서 UI 예시 화면의 줄들은 서버 패킷과 이렇게 이어집니다. 서버가 이 순서대로 보내 주면 클라이언트는 예시와 같은 화면을 그릴 수 있습니다.

제안서 예시 화면 (B)B가 받은 패킷

[*] 키 교환 완료 · 안전번호 4821 0937서버 → 클라 HELLO (A의 공개키). 키 교환과 안전번호 계산은 클라이언트가 함

B> /open 3 → [!] 조각 1/2 확보 - C의 승인이 필요합니다3번 OPEN_REQ를 보내고 4번 LOCK을 받음

왜 안전한가: 서버가 가진 건 봉인된 조각 2개뿐이고, 각각 B와 C의 개인키가 있어야 열립니다. 6번에서 C가 보낸 조각도 B의 공개키로 다시 봉인돼 있어서 서버는 끝까지 L을 알 수 없습니다.
주의: 서버가 잠금 번호(seq)를 붙이기 때문에, 클라이언트가 잠금 암호문을 만들 때 추가 데이터(AD)에 seq를 넣으면 복호화가 실패합니다. 잠금 암호문의 AD에는 from만 넣도록 암호 담당과 맞춰 주세요.

6시연 옵션 ("나쁜 서버" 모드)

팀 기획서 4절의 공격 시연 3종을 서버가 직접 재현합니다. 옵션을 켜면 시작할 때 [DEMO] 나쁜 서버 모드: tamper처럼 크게 출력해서, 일반 실행과 헷갈리지 않게 합니다.

옵션서버 동작클라이언트에서 보여야 할 것
--tamper중계하는 MSG 3개마다 하나씩 암호문 마지막 바이트를 ^= 0x01[!] 변조 감지 - 메시지 폐기
--replay받는 사람별로 직전 MSG 사본을 갖고 있다가, MSG 3개마다 하나씩 새 메시지 뒤에 옛 사본을 한 번 더 보냄[!] 순서번호 불일치
--mitm시작할 때 서버 자신의 키 쌍 2개를 만들고, 공개키를 배포할 때(HELLO) 모두 서버 것으로 바꿔치기A와 B가 /verify로 본 안전번호가 서로 다름

--mitm은 바꿔치기까지만 합니다. 서버가 양쪽과 각각 키 교환을 해서 실제로 엿보려면 서버에 래칫까지 넣어야 해서 일이 커집니다. 바꿔치기만 해도 ① 안전번호가 다르고 ② A와 B의 키가 달라져 메시지가 복호화되지 않으니, "안전번호를 비교하면 중간자를 잡는다"를 보여주기에는 충분합니다. 이 옵션 때문에 서버도 libsodium을 링크합니다(crypto_kx_keypair, crypto_box_keypair만 사용).

7코드 뼈대

방향을 보여주는 뼈대입니다. 오류 처리는 줄였고, 컴파일해서 확인한 코드가 아니니 1단계부터 직접 빌드하면서 채워 주세요.

net.h: 서버와 클라이언트가 같이 쓰는 부분

#include <stdint.h>
#include <stddef.h>

#define NAME_LEN  16
#define NONCE_LEN 24
#define HDR_LEN   (1 + NAME_LEN + NAME_LEN + 8 + NONCE_LEN)   /* 65 */
#define MAX_BODY  65536

enum { T_HELLO = 1, T_MSG, T_LOCK, T_OPEN_REQ, T_SHARE, T_SYS };

struct packet {
    uint8_t  type;
    char     from[NAME_LEN], to[NAME_LEN];
    uint64_t seq;
    uint8_t  nonce[NONCE_LEN];
    uint32_t body_len;
    uint8_t  body[MAX_BODY];
};

struct conn {                        /* 받는 중인 바이트를 모아 두는 곳 */
    int     fd;
    uint8_t buf[4 + HDR_LEN + MAX_BODY];
    size_t  len;
};

int net_listen(int port);
int net_connect(const char *host, int port);
int send_packet(int fd, const struct packet *p);
int conn_read(struct conn *c);                          /* recv 한 번: >0 받음, 0 끊김, -1 오류 */
int conn_take(struct conn *c, struct packet *p);        /* 1 꺼냄, 0 아직 덜 옴, -1 잘못된 길이 */

net.c: 직렬화와 "덜 온 패킷" 처리

int send_packet(int fd, const struct packet *p)
{
    static uint8_t out[4 + HDR_LEN + MAX_BODY];
    uint32_t len = HDR_LEN + p->body_len;
    uint32_t nlen = htonl(len);
    uint8_t *q = out;

    memcpy(q, &nlen, 4);              q += 4;
    *q++ = p->type;
    memcpy(q, p->from, NAME_LEN);     q += NAME_LEN;
    memcpy(q, p->to, NAME_LEN);       q += NAME_LEN;
    for (int i = 7; i >= 0; i--)      /* seq: 큰 자리부터 */
        *q++ = (uint8_t)(p->seq >> (i * 8));
    memcpy(q, p->nonce, NONCE_LEN);   q += NONCE_LEN;
    memcpy(q, p->body, p->body_len);

    size_t total = 4 + len, sent = 0;
    while (sent < total) {            /* send는 일부만 보낼 수 있다 */
        ssize_t n = send(fd, out + sent, total - sent, MSG_NOSIGNAL);
        if (n <= 0) return -1;
        sent += (size_t)n;
    }
    return 0;
}

int conn_read(struct conn *c)
{
    ssize_t n = recv(c->fd, c->buf + c->len, sizeof c->buf - c->len, 0);
    if (n > 0) c->len += (size_t)n;
    return (int)n;
}

int conn_take(struct conn *c, struct packet *p)
{
    uint32_t len;
    if (c->len < 4) return 0;
    memcpy(&len, c->buf, 4);
    len = ntohl(len);
    if (len < HDR_LEN || len > HDR_LEN + MAX_BODY) return -1;
    if (c->len < 4 + len) return 0;  /* 아직 덜 왔음: 다음 recv를 기다림 */

    const uint8_t *q = c->buf + 4;
    p->type = *q++;
    memcpy(p->from, q, NAME_LEN);     q += NAME_LEN;
    memcpy(p->to, q, NAME_LEN);       q += NAME_LEN;
    p->from[NAME_LEN - 1] = p->to[NAME_LEN - 1] = '\0';
    p->seq = 0;
    for (int i = 0; i < 8; i++) p->seq = (p->seq << 8) | *q++;
    memcpy(p->nonce, q, NONCE_LEN);   q += NONCE_LEN;
    p->body_len = len - HDR_LEN;
    memcpy(p->body, q, p->body_len);

    c->len -= 4 + len;                /* 꺼낸 만큼 앞으로 당긴다 */
    memmove(c->buf, c->buf + 4 + len, c->len);
    return 1;
}

struct packet은 64KB가 넘으니 함수 안 지역 변수로 두지 말고 static이나 전역으로 하나만 둡니다. 스택이 넘칠 수 있습니다.

server.c: poll 루프

#define MAX_CLIENTS 16

struct client {
    struct conn c;
    char    name[NAME_LEN];
    uint8_t kx_pk[32], box_pk[32];
    int     registered;
};

static struct client clients[MAX_CLIENTS];
static int nclients;
static struct packet pkt;

int main(int argc, char **argv)
{
    /* argv에서 --tamper / --replay / --mitm 확인 */
    int lfd = net_listen(9000);
    struct pollfd fds[1 + MAX_CLIENTS];

    for (;;) {
        fds[0] = (struct pollfd){ .fd = lfd, .events = POLLIN };
        for (int i = 0; i < nclients; i++)
            fds[1 + i] = (struct pollfd){ .fd = clients[i].c.fd, .events = POLLIN };
        poll(fds, 1 + nclients, -1);

        if (fds[0].revents & POLLIN)
            add_client(accept(lfd, NULL, NULL));   /* 꽉 찼으면 SYS 보내고 close */

        for (int i = nclients - 1; i >= 0; i--) {   /* 뒤에서부터: 도중에 지워도 안전 */
            if (!(fds[1 + i].revents & (POLLIN | POLLHUP | POLLERR))) continue;
            struct client *cl = &clients[i];
            int r;
            if (conn_read(&cl->c) <= 0) { drop_client(i); continue; }
            while ((r = conn_take(&cl->c, &pkt)) == 1)
                if (handle_packet(i, &pkt) < 0) break;  /* -1이면 handle_packet이 이미 drop_client(i)를 함 */
            if (r < 0) drop_client(i);
        }
    }
}

drop_client(i)는 소켓을 닫고 마지막 칸을 i번 자리로 옮겨 표를 채웁니다. 루프를 뒤에서부터 돌기 때문에 이미 확인한 칸만 옮겨지고, 확인할 칸은 건너뛰지 않습니다. 단, handle_packet 안에서 다른 클라이언트에게 보내다 실패해도 그 자리에서 지우지 마세요. 표가 루프 도중에 섞입니다. 실패는 무시하면, 그 소켓은 다음 poll에서 끊김으로 잡혀 정상 경로로 지워집니다. handle_packet은 type별 switch 하나에 4·5절 규칙을 그대로 옮기면 됩니다.

8단계와 확인 방법

팀 기획서 10-3의 2·3·5·7·8단계 중 서버 몫을 잘게 나눈 것입니다. 확인 방법을 통과해야 다음 단계로 넘어갑니다. 제안서 일정의 7주차 "서버간 통신"은 서버가 하나뿐이라 실제로는 클라이언트–서버 중계 통신이고, 수정본도 이렇게 고쳤습니다.
